# Discovery playbook

## Discovery order

### 1. Warm graph

Check existing professional relationships first when available:

- current/former customers,
- prior opportunities and lost deals,
- founder/team network,
- investors/advisors,
- ecosystem/integration partners,
- newsletter/community members,
- users of adjacent products or open-source projects.

Warmth is an **access advantage**, not a partnerability score. Do not rank a weak candidate highly because an introduction is easy.

### 2. Problem-first public signals

Search for the work, pain, and trigger:

- repeated manual workaround,
- migration or switching friction,
- "looking for" / feature-gap language,
- job postings revealing the workflow,
- public implementation pain,
- launch/scale/regulatory/technology transition,
- public GitHub issues or technical docs when relevant,
- customer case studies revealing the operating model.

### 3. Ecosystem adjacency

Look for organizations already close to the problem:

- users/customers of substitutes,
- integration ecosystems,
- agencies/consultancies operating the workflow for many clients,
- open-source maintainers/users,
- vendors serving the same user role without competing directly.

### 4. Coverage search

After learning the vocabulary, use company databases/directories to fill segment gaps. Firmographics identify candidates; they do not prove pain.

## Search waves

**Wave A — universe**: collect 3–5x the intended outreach slate when evidence density permits. Capture company, domain, tentative signal, source/date, segment, and warm path.

**Wave B — evidence qualification**: obtain at least one credible problem/trigger source and one source supporting entity/capability/fit. Add stakeholder/contact-path hypothesis.

**Wave C — deep diligence**: research roughly 2x the desired slate or the smallest set that covers the Learning Contract. Resolve urgency, implementation plausibility, credibility, conflict, and highest-value unknowns.

**Wave D — counter-search**: seek disconfirming evidence for top candidates: initiative cancelled, workflow changed, incompatible stack, conflict, stale team role, one-off use case, procurement burden, or material claim contradiction.

## Query families

Adapt to real market vocabulary. Examples:

- `"[pain phrase]" [role/industry]`
- `"[workaround]" "[workflow]" company`
- `"migrating from" [alternative]`
- `"looking for" [solution category]`
- `[company] [workflow] case study`
- `[company] [relevant role] hiring`
- `site:github.com [technology/workflow] [company]`
- `[company] [integration/initiative]`

Do not run one generic query mechanically across dozens of companies.

## Candidate record

Capture:

- canonical company/domain + aliases,
- discovery source and date,
- segment / intended variation dimension,
- problem/trigger evidence,
- capability/implementation evidence,
- stakeholder path,
- warm relationship path if any,
- Learning Contract hypotheses covered,
- open unknowns,
- rejection reason if dropped.

## Stop rule

Stop expanding when one additional search wave produces little new hypothesis coverage, little new segment coverage, or mostly candidates weaker than the current cutoff. Prefer a smaller evidence-backed slate to padded coverage.
