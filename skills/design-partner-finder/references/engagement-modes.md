# Engagement modes

Choose the relationship type before scoring. The same company can be appropriate for one motion and wrong for another.

| Mode | Primary question | Minimum evidence before activation | Commercial expectation | Typical failure mode |
|---|---|---|---|---|
| `RESEARCH_PARTNER` | Is the problem/workflow real and worth solving? | credible pain/workflow + relevant user access | none required | mistaking interview enthusiasm for product demand |
| `DESIGN_PARTNER` | Can we co-shape a transferable product? | confirmed pain + user/champion + repeated feedback capacity | optional/stage-dependent | custom consulting disguised as product work |
| `BETA_PARTNER` | Does the product work in real conditions? | usable product + implementation path + actual user | optional | passive beta access with no meaningful usage |
| `PAID_PILOT` | Does the product create enough value to justify commercial adoption? | live value hypothesis + implementation + authority/procurement path | explicit | slow enterprise sales process masquerading as learning |
| `LIGHTHOUSE` | Can a successful customer create credible market proof? | demonstrated value + credible story + reference willingness | normally customer-like | selecting prestige before product fit |

## Routing rules

- Prefer `RESEARCH_PARTNER` when the product is still a mock, prototype, concierge workflow, or the problem itself is uncertain.
- Prefer `DESIGN_PARTNER` when product behavior and workflow fit are still changing materially.
- Prefer `BETA_PARTNER` when core behavior exists and the main unknowns are usability, robustness, edge cases, or deployment.
- Prefer `PAID_PILOT` when the main unknown is production/commercial adoption rather than core problem discovery.
- Use `LIGHTHOUSE` only after the company has a real success story or a credible path to one. Lighthouse value never overrides weak pain/learning fit.

## Payment is not a universal gate

Do not encode "design partners must pay" or "design partners should never pay" as a universal rule.

- Early problem/product discovery: optimize first for high-fidelity learning and real usage.
- Enterprise/production pilots: meaningful commercial commitment can be useful evidence of internal priority and procurement reality.
- If payment materially slows learning, distinguish a design partnership from the later commercial contract.
- If free access creates low commitment, require another form of skin-in-the-game: implementation work, named users, data/system access, recurring meetings, or measurable pilot use.

## Conversion

A design partner does not fail merely because it does not convert. Track separately:

- learning value,
- product value demonstrated,
- implementation feasibility,
- willingness/ability to buy,
- reference potential.
